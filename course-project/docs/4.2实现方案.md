# 4.2 缺陷迁移实现方案

本文件是分阶段设计。第一阶段已实现模板导入、画像、T10/T11 静态匹配和审核计划，进度与边界见 [实现与验证记录](4.2阶段1实现与验证.md)。其余内容仍为后续计划；下表候选缺陷尚未被真实实验确认。

输入依据：templates/chaosblade_defect_templates.md 的 15 条草稿模板。平台沿用 main 基线，开发服务采用 Java 21 / Spring Boot 3.5.5。目标源码本次检查版本为 OpenTelemetry Demo 的 85c2cb253ae3519ef2b3a02984c32614106de5ea；真正实验还必须核对运行镜像、部署配置和该源码一致。

## 1. 目标与范围

开发独立服务 svc-defect-transfer（建议端口 8107），接收模板和目标系统资料，输出：

1. 模板各角色对应哪个服务、接口或实例。
2. 每个成立条件满足、不满足或未知，以及支持判断的证据。
3. 可执行的故障配置、负载、观察与恢复计划；无法执行时给出原因。
4. 实验是否真正施加到目标、机制是否激活、后果是否出现、证据是否完整。
5. 有明确适用范围的结论，以及与人工判断和修复前版本的对照。

核心工作是将模板变成可检验的假设。系统变慢只是结果之一，不能代替对具体失效机制的验证。

第一版不实现通用源码理解器、不自动修业务代码、不做完整新前端，也不承诺 15 条全部可执行。先用 API、报告文件和少量可扩展适配器跑通核心链路。

## 2. 输入模板的使用方式

### 2.1 保留原始草稿，另做可执行定义

模板已经包含 roles、applicability、defect_conditions、activation、failure_chain、oracles、fix_signatures 和 provenance，应直接保留，避免另造一份缺少信息的格式。

但其中 expr 和 oracle 都是自然语言，计算机不能可靠地直接执行。因此每条模板配一份 OperationalSpec（可执行定义），按原始 A1/D1 等编号关联，包含：

- predicate：查询什么事实、使用什么比较规则。
- parameterRule：相对参数如何计算，单位、边界和缺失处理。
- observationRule：从哪个数据源取信号，以什么实验窗口、关联键和阈值判断。
- requiredCapabilities：执行器和观察器需要支持的能力。
- review：是否人工确认、版本和确认理由。

这份定义描述通用判断规则，不写目标系统服务名，也不直接填“此服务有缺陷”。角色到服务的对应必须由匹配结果生成，避免把人工答案包装成自动匹配。

示例（设计表示，尚非实现的 YAML 解析协议）：

    templateId: DT-MQ-REDELIVER-001
    conditionId: A2
    predicate:
      operator: ANY
      operands:
        - fact: consumer.sideEffectBeforeCommit
          equals: true
        - fact: consumer.commitMode
          equals: periodic
    requiredEvidence: [codeOrEffectiveConfig]

缺少事实时返回 UNKNOWN；禁止将自然语言 expr 或参数字符串直接交给 eval、Shell 或任意代码执行。参数解释器第一版只支持引用、加减乘除及带单位的数值。

### 2.2 草稿来源与目标证据分开

这 15 条不是从具体事故报告抽出的已确认模板，provenance 仍为空。第一版可作为用户提供的假设输入进行验证，但报告必须标记 draft。

“模板来源于何处”和“在本目标系统中发现什么证据”是两类信息：

- TemplateProvenance：事故 URL、原文片段、字段证据状态。
- TargetEvidence：源码位置、实际配置、运行记录、实验结果。

给草稿补上一个看似相关的事故链接，不能代替逐字段核实；不得将本次设计宣传为已完成 4.1。草稿能否作为课程最终验收输入，需向老师确认。

## 3. 先核实目标系统，避免按名称猜缺陷

本次源码阅读得到以下线索，均不是实验证实：

| 位置 | 已看到的内容 | 对选题的影响 |
| --- | --- | --- |
| checkout/main.go 的 PlaceOrder、sendToPostProcessor | 先执行支付等步骤，再发 Kafka；发布失败记录日志 | T11 值得优先检查 |
| checkout/kafka/producer.go | RequiredAcks=NoResponse；另有协程读取 producer.Errors() | 本地“发送成功”不能证明 broker 已接收；错误与具体订单的关联也需补齐 |
| accounting/Consumer.cs、Entities.cs | 定时自动提交位点；订单主键；SaveChanges；捕获唯一键冲突 | T10 是候选，且已有业务键防护线索；需要实际重投后确认防护是否覆盖副作用 |
| checkout/main.go 的 mustCreateClient、chargeCard | 本段未显式配置重试策略，传递调用上下文 | T01、T03 不能直接认定成立；还要检查网关、gRPC 有效配置和运行调用 |
| payment/charge.js | 模拟交易、日志和计数，没有真实银行扣款账本 | 不能把 transactionsCounter 当成真实重复扣款记录；T01 需要可审计的实验副作用 |
| cart/ValkeyCartStore.cs | 购物车直接保存在 Valkey，未命中返回空购物车 | 不能因有 Valkey 就套用 T06/T07 的“缓存前有数据库”条件 |
| checkout/main.go 的 Check | 直接返回健康状态 | 这一路径没有看到依赖健康检查，适合 T12 的负例线索；仍需实际 K8s 探针配置 |
| frontend-proxy/envoy.tmpl.yaml | 路由超时存在 0s 配置，frontend 上游采用 ROUND_ROBIN | T13 要核对实际实例发现和连接复用，不能假设每个请求必然均分 |

本地源码没有提供完整当前集群的部署状态，不能据此声称所有副本数、健康检查或数据库复制配置已确认。

## 4. 模板预筛与五条深度实验

### 4.1 全部 15 条先给出候选与缺口

| 模板 | 初步处理 | 必须补查的内容 |
| --- | --- | --- |
| T01 重试重复写 | 备选，暂不承诺原版可复现 | 写请求超时重试、稳定业务键、真实实验副作用、响应后置延迟能力 |
| T02 多层重试放大 | 暂缓 | 两层有效重试、后端容量标定、持续负载和恢复窗口 |
| T03 超时倒挂 | 五条深度候选 | 逐跳有效超时、最大尝试次数、取消传播和取消后的继续处理证据 |
| T04 慢调用熔断 | 暂缓 | 是否实际存在熔断器、有界工作池与慢调用统计 |
| T05 共享资源池 | 暂缓 | 具体池对象和共享引用，不能仅凭同一个进程判断 |
| T06 缓存击穿 | 暂缓 | 缓存未命中是否回数据库；热点负载与后端容量 |
| T07 缓存旧值 | 暂缓 | 是否有“先写库再删缓存”的业务路径 |
| T08 切主旧连接 | 暂缓 | 实际数据库主备、自动切换与客户端连接配置 |
| T09 复制延迟 | 暂缓 | 是否有读写分离和异步复制副本 |
| T10 重投重复消费 | 优先，五条深度候选 | 消费/位点顺序、重投证据、已有数据库去重是否有效 |
| T11 副作用后丢消息 | 优先，五条深度候选 | 订单关联、broker 接收证据、实际持久化补偿是否存在 |
| T12 探针级联重启 | 五条深度候选 | 实际 K8s liveness 内容、至少两个副本、探针是否访问下游 |
| T13 慢实例不摘除 | 五条深度候选 | 至少三个实例、逐实例流量、健康状态和有效路由策略 |
| T14 降级同故障域 | 暂缓 | 是否确有降级分支，降级分支实际访问的对象 |
| T15 锁租约过期 | 暂缓 | 租约锁、多个竞争者、续约行为和防护令牌 |

“暂缓”表示目前资料或实现成本不合适，不是已经证明不适用。必须拿到完整相关证据，才能把某条必要条件判为 FALSE。

### 4.2 五条是计划，不是预设五个正例

第一轮优先顺序：T11 → T10 → T13 → T12 → T03。

- T11：优先利用现有下单到消息队列链路，先补全可信观测。
- T10：检验已有去重防护，不要求原版必须产生重复。
- T13：可在独立实验部署中扩为三个实例，检查实际路由分布。
- T12：可能成为已有防护或不适用的负例；不得为了凑数宣称原版存在级联重启。
- T03：先确认超时与取消条件，如果原版不满足则如实记录。

如果老师要求五条都必须形成可执行动态实验，且原系统无法满足条件，则使用明确标注的“实验变体”：在同一目标系统中通过配置覆盖或小补丁构造已知缺陷版与修复版。补丁只建立实际机制，不直接伪造 oracle 结果；原版、观测补丁、缺陷补丁、修复补丁要分开保存。

实验变体必须经老师确认可作为验收范围，不能把人为构造的缺陷写成原系统已有缺陷。若不允许构造，应预筛后更换五条或更换合适目标，不能硬凑。

## 5. 独立服务的职责与复用边界

建议新增 platform/svc-defect-transfer，作为独立 Spring Boot 服务。自身数据使用独立表或数据库；不跨服务直接读写平台已有表。

处理流程：

    模板草稿 + 可执行定义
              ↓
    收集目标资料 → 建系统画像 → 匹配角色与条件
              ↓
    检查执行与观测能力 → 计算参数 → 生成实验计划
              ↓
    正常基线 → 真故障 + 持续负载 → 恢复后观察
              ↓
    核对证据 → 判定 → 保存报告 → 与人工、修复版对照

复用现有公开接口：

| 能力 | 已有接口或模块 | 使用方式 |
| --- | --- | --- |
| 系统、故障类型和任务信息 | svc-task-resource 的 /api/systems、/api/fault-types、/api/probe-tasks | 读取资料；需要在平台展示时写入已有任务 |
| 调用关系 | svc-topo 的 POST /v1/topology/byapi 等 | 读取服务关系，按返回的系统/API 标识关联 |
| 故障配置保存 | /api/task-fault-configs | 在已有任务和节点存在时，按现有 DTO 保存生成结果 |
| 故障执行 | svc-fault-scheduler 的 POST /api/faults/execute | 提交完整 CR 或包含 spec 的配置 |
| 故障状态与清理 | GET /api/faults/{bladeName}/status、DELETE /api/faults/{bladeName} | 跟踪注入结果并显式恢复 |
| 指标 | /v1/metrics/byapi | 复用延迟、错误率等通用指标，但不足以证明消息丢失或重复副作用 |

配置与源码由用户提供的版本快照读取；运行部署与实例资料可由只读采集器导入，不臆造平台尚不存在的源码接口。

本次不直接调用原 ExecutionOrchestrator 跑缺陷验证：原流程先注入、录下错误响应、恢复，再以拦截响应跑组合测试。T10/T11 等涉及真实写入、消息提交和恢复的顺序，必须在真实故障窗口内运行真实业务。已有回放能力可用于请求准备，不能代替机制验证。

故障类型字典为空、执行器版本或插件不支持时，输出明确缺口；不能把请求被调度服务接受等同于目标故障支持。网络延迟、丢包等模型也必须按实际 Operator、执行器和故障字典版本验证参数，文档不先写一段未经验证的 CR 当成可运行结果。

## 6. 对象、关系和存储

| 对象 | 通俗理解 | 核心职责 |
| --- | --- | --- |
| DefectTemplate | 一类问题的说明书 | 保存原始模板、版本、草稿和来源状态 |
| OperationalSpec | 程序能执行的检查表 | 把 A1、D1、oracle 对应到事实、运算符和取证规则 |
| SystemProfile | 本次实验的系统档案 | 服务、接口、调用边、实例、技术能力、配置和版本快照 |
| Evidence | 每项判断的依据 | 源码引用、配置项、日志、Trace、指标、数据库结果及覆盖范围 |
| MatchResult | 模板与系统的对应表 | 角色绑定、逐条件结果、未满足项和原因 |
| ExperimentPlan | 实验操作单 | 目标、注入点、实际参数、负载、观察窗口、恢复方法 |
| ExperimentRun | 一次实际执行 | 阶段状态、故障标识、业务键集合、证据和清理状态 |
| VerificationConclusion | 有依据的判定 | 结论、适用范围、不确定项及与前次实验的比较 |

关系：Template + OperationalSpec + Profile 产生 MatchResult；匹配后产生 Plan；Plan 可以执行多次 Run；每个 Run 产生一份 Conclusion，并引用其实际证据。

不可把结论和任务状态混在一个字段。任务可能执行完成，但结论仍是证据不足；结论已经生成，也可能故障清理失败。

第一版六张主要表足够：

- defect_template：原模板 + OperationalSpec 的版本化 JSON。
- system_profile：不可变的画像快照和事实索引 JSON。
- match_result：绑定与条件评估。
- experiment_plan：生成配置及执行约束。
- experiment_run：状态、故障句柄、证据索引、重复次数和错误信息。
- verification_conclusion：判定、逐 oracle 结果和比较依据。

少量证据元数据可先存 JSON，大日志保存为文件引用及哈希；不一开始再建图数据库和消息中间件。更新模板或源码时生成新快照，不覆盖历史结果。

## 7. 画像与技术适配：只做任务需要的深度

### 7.1 统一事实

例如：

    subject: checkout -> payment / Charge
    fact: retry.maxAttempts
    value: 2
    unit: count
    evidence: source/config reference
    certainty: CONFIRMED | INFERRED | UNKNOWN
    scope: specific call edge and deployment revision

上例数字仅说明格式，未表示真实 checkout 已配置两次尝试。

超时应记录在具体调用边、客户端和接口上，而不是只给一个服务放一个 timeout。需要同时区分总尝试次数、额外重试次数、每次超时、总预算和等待时间。

事实还需要记录源码提交、部署版本、来源位置和覆盖范围。未搜索到重试代码，不能直接记“无重试”；还需确认有效配置、代理、客户端默认行为等。不能完整确认时保留 UNKNOWN。

### 7.2 两层扩展接口

技术适配器只负责取事实；机制规则负责用事实作判断：

    ProfileAdapter.supports(source)
    ProfileAdapter.extract(source) -> facts + evidence + missingCapabilities

    PredicateEvaluator.evaluate(rule, bindings, profile) -> TRUE / FALSE / UNKNOWN

    FaultExecutor.supports(planRequirements)
    FaultExecutor.execute/recover(plan)

    EvidenceCollector.collect(run, observationRule)
    VerdictEvaluator.evaluate(observations, match, comparison)

建议第一版适配器：Kubernetes 部署/探针；Go/gRPC 调用与上下文；.NET/Kafka 消费与数据库去重；Kafka 发布与确认。这里按“技术与功能”划分，不写成只识别某个服务名称的硬编码。

人工补充允许作为单独 ManualEvidence 输入，标记来源、审核者和理由；不能和自动提取混为一谈。报告分别统计自动覆盖和人工补充比例。

不要求程序理解所有 Go/C# 控制流。先支持几个能清楚说明边界的结构化配置与代码模式，复杂情况返回待审核。大模型可建议候选代码位置或写解释，最终判断必须引用可核对的事实，不以其自由回答直接代替匹配。

## 8. 匹配算法：先有角色，再逐条查条件

1. 按角色 needs 从画像中筛候选，例如“能发布消息”和“能消费消息”。角色缺失只在采集范围完整时才可确认为不存在。
2. 按 topology 约束拼出实际调用关系，避免对所有服务随意组合。角色基数约束也必须检查，例如 T13 至少三个实例；可选角色 guard 不存在与 guard 未识别要分开。
3. 评估 applicability：有确定 FALSE 就记录该绑定不适用；有未知就记录缺什么资料。
4. 对适用绑定评估 defect_conditions，不因发现防护而丢弃候选。防护也是需要验证的重要情况。
5. 检查执行器和观察器能力，形成执行就绪结果。
6. 为每个匹配保留原条件编号、事实值、证据引用和推理步骤。

三值逻辑：ALL 中任何 FALSE 则 FALSE，全部 TRUE 才 TRUE，其余 UNKNOWN；ANY 中任何 TRUE 则 TRUE，全部 FALSE 才 FALSE，其余 UNKNOWN。

系统层面不能因为一个绑定不适用就宣布该模板对整个系统不适用。只有候选枚举和资料覆盖完整、所有可能绑定都被排除时，才能得出该范围的“不适用”；否则保留未知候选。

置信度可用于排序，但不能用一个百分比分数覆盖未知条件。满足两个条件、第三个未知，不是“67% 匹配所以可以实验”。

## 9. 实验编译与执行

Plan 至少保存四部分：

- 故障计划：抽象 fault_type、具体角色绑定、Pod UID/端口/方向、注入点、CR 和恢复动作。
- 负载计划：接口、请求内容、业务键、并发和速率、预热、请求总数。
- 观测计划：取证数据源、采样/覆盖要求、正常/故障/恢复窗口、阈值。
- 参数依据：每个值由哪条画像事实计算得出，单位换算和选择理由。

相对参数只在真实数值存在时求值。例如目标实际 timeout=200ms，T01 建议 delay=300ms；实际没配置超时，或为无限超时，则该表达式不可编译，不填随意默认值。

参数满足上限也不能简单截断后仍称原计划可执行；如果截断后不足以触发模板，返回参数不可实现，并报告原因。故障范围、最大持续时间、最大负载需在实验部署配置中显式给出。

特别能力约束：

- T01 的 after_side_effect 要保证副作用已经发生、但响应被拖慢；普通请求入向延迟不等价。响应方向网络延迟只有在方法、方向和时序证据足够时才能用于此语义。
- T10 可按模板许可进行概率杀进程，但必须看到同一消息真的重投；进程重启本身不够。确定性测试可以在副作用后、提交前加观测/同步点，必须标明这是实验补丁。
- T13 要精确选择一个实例；把整个服务都拖慢，不再是该模板。
- T15 的临界区注入必须能够识别临界区，不能随便暂停一个实例后就称精准触发。

不支持时返回 UNSUPPORTED，不自动退化。概率窗口作为显式执行策略，必须有 oracle 证实命中。

运行状态建议：CREATED → PREFLIGHT → BASELINE → INJECTING → EXERCISING → RECOVERING → OBSERVING_RECOVERY → EVALUATING → COMPLETED；异常为 FAILED/CANCELLED，并单独保存 cleanupStatus。

故障标识持久化；恢复放在 finally 路径并辅以调度 TTL。恢复失败、观察器中断、基线不健康必须写明，不生成“缺陷不存在”的结论。定期核对遗留故障，重复请求通过 idempotencyKey 避免重复注入。

T02 明确需要故障移除后的长窗口。T11 要等发布重试、消费者处理恢复后再判断，不能一断网就把所有下游未处理订单记作永久丢失。

## 10. 证据与结论：补充模板的判定边界

### 10.1 四种不同问题必须分别回答

| 维度 | 问题 | 例子 |
| --- | --- | --- |
| Exposure：扰动有效 | 目标是否真的遭遇计划条件？ | checkout 到 Kafka 的链路确实中断，期间有真实下单请求 |
| Activation：机制激活 | 模板中的机制是否实际启动？ | 同一订单消息被重投，或调用发生重试 |
| Consequence：后果 | 是否出现模板预测的损害？ | 同一订单重复入账，或超过观察期限仍缺少下游记录 |
| Protection：防护 | 有无实际生效的防护？ | 重投时数据库主键拦住重复写，持久化重试在恢复后补发 |

故障资源 Running 只是执行状态，不是 Exposure 充分证据。采样 Trace 中没有某个事件也不证明事件没发生。

一个 oracle 结果保存 TRUE/FALSE/UNKNOWN、数据覆盖度、时间窗、样本数、证据引用和理由。指标源断连、日志缺失和采样率不足返回 UNKNOWN；不能当成零。

业务重复与消息丢失要用业务键或 topic/partition/offset 关联；Trace 用于解释过程，数据库/事件审计用于数结果。业务键放在日志和 Trace 中，避免把每个订单编号做成指标标签造成大量指标。不同实例的时钟偏差必须考虑，严格先后关系尽量用同一消息标识和已记录的业务事件顺序核对。

### 10.2 结论的推荐表示

将“实验是否可做”和“缺陷判断”分开存储：

- suitability：APPLICABLE / NOT_APPLICABLE / UNKNOWN。
- readiness：READY / UNSUPPORTED / EVIDENCE_UNAVAILABLE / PARAMETER_UNRESOLVED。
- verdict：PRESENT / NOT_TRIGGERED / PROTECTED / INCONCLUSIVE。
- comparison：REPAIR_SUPPORTED / MECHANISM_REMOVED / NOT_COMPARABLE / NONE。

用户报告将这些字段合成易懂中文，不让一个状态枚举承担所有含义。

判定顺序：

1. 在明确对象范围内，必要条件确认为不满足 → 不适用，不外推成系统不存在任何风险。
2. 关键条件未知、必要执行能力或观测缺失 → 无法判定，列出缺口。
3. 故障没成功施加、负载没到达目标或恢复失败影响结论 → 实验无效/无法判定。
4. Exposure 已确认、机制信号在完整观测下仍未出现 → 未被触发；不推出缺陷不存在。
5. 激活与有害后果都被证实，且与本次扰动/业务键关联 → 本次实验支持缺陷存在。
6. 有效挑战下未出现后果，而且确认防护路径生效 → 本次条件下已防护。
7. 静态缺陷条件成立但充分挑战没有后果，或静态防护与动态损害矛盾 → 无法判定，检查画像、条件与观察器，不能默认忽略冲突。

“已修复”需要有修复前的已确认缺陷、明确的代码/配置变化、可比较的负载和扰动及修复后的防护证据。第一次见到正常表现只能写“已防护”或“未观察到问题”。

### 10.3 对原始判定规则的必要补充

原文件建议 activation 未出现即未触发，但修复有时会消除 activation 本身：

- T12 修复为存活检查只看进程后，下游断连时 liveness 不该失败。
- T01 若修复为不对超时写操作重试，retryCount 不该大于零；原 applicability 中“超时重试”也可能不再成立。
- T11 修复为持久化待投递事件后，发布尝试可能仍失败，但“失败并丢弃”不该再发生。

处理方式：在 OperationalSpec 中增加 fix-independent Exposure（修复后仍可证实的挑战条件）和 Protection 观测。原模板文本不偷偷修改，登记解释规则版本及审核理由。

对修复后结构改变的情况，保留原版的角色绑定进行对照评估，同时按新画像记录当前 applicability；报告写“原匹配机制被移除，对照支持修复”，不强行把已不适用的修复版塞回旧条件，也不要求已移除的机制再次触发。

三次重复是模板建议的起点，不是统计上证明不存在的保证。记录每次有效挑战、触发次数、后果次数；0/3 只表示该样本和窗口中没有观察到，不能证明长期绝无问题。

## 11. 五条深度实验的具体设计

### E1：T11 下单后消息未可靠到达

角色候选：producer=checkout，broker=Kafka，downstream=accounting。

先做：

- 固定运行镜像与代码版本，确认 Kafka 功能启用、topic 和消费者组一致。
- 检查现有补偿路径；Producer.RequiredAcks=NoResponse 意味着不能把 producer.success 指标当 broker 接收证明。
- 给每次下单建立稳定 orderId 与消息关联，观测支付/订单接受事件、发送尝试、broker 接收及 accounting 落库结果。
- 现有多个逻辑同时读 producer.Errors()，需要核实具体订单能否关联。无法关联时记证据不足；可增加明确标注的观测补丁，不能把没有错误日志当发送成功。

实验：正常基线 → 对 checkout 到 Kafka 的指定链路制造中断 → 期间下单 → 恢复 → 等待已登记的投递与消费期限 → 对照同一批业务键。

参数：依据实际总发送预算计算中断时间，包含每次尝试、退避及总 deadline，不能直接假设 publish_timeout × publish_retries 就是总预算。若 retries=0，不能算出 0 秒中断。

判定：必须证明业务副作用发生、消息发送或到达失败，并在恢复且消费者已恢复后仍缺少对应处理。只能说“截至观察期限仍缺失”，不能用有限实验宣称永远不会到达。

原模板严格要求发布失败计数，若 ack=0 使该信号不可得，则原版结果应为 EVIDENCE_UNAVAILABLE；要修改 operational oracle 采用明确的 broker 接收/发送链路证据，需版本化审核，不能默改标准追求正例。

修复路线：持久化业务事件与待投递状态、独立重试或对账补发。只有本地业务状态与 outbox 在同一数据库事务内，才能称事务性发件箱；远程支付、发货不能直接与本地 outbox 原子提交。对这些外部副作用需要幂等和恢复协调，不能一句“加 outbox”就声称覆盖所有崩溃窗口。

建议以 T11 为主展示对照：缺陷版 + 足够长中断；同缺陷版 + 不足触发/未出现发布失败的短扰动；修复版 + 同等有效挑战。短扰动没有触发需由 oracle 证实，不能预设结果。

### E2：T10 消费重投与已有去重

角色候选：broker=Kafka，consumer=accounting，guard=数据库主键/事务。

以同一 orderId、topic/partition/offset 跟踪副作用及提交。先确认重复投递实际发生；只有进程重启或消费日志重复，不能直接判重复入账。

当前代码已有唯一键冲突处理，预期应检验“消息重投但数据库仅有一份有效业务结果”。若记录完整且防护确实生效，可判已防护；存在数据主键不等于已经证明全部副作用幂等。

如果需构造正例：在实验变体中引入真实的非幂等副作用路径，并提供确定的副作用后/提交前同步点；修复版改为稳定业务键去重且与副作用同事务。不能仅删除一个异常处理块就声称已经去掉数据库唯一约束。

对随机杀进程模式，至少多轮并报告命中率；没有命中未提交窗口时输出未触发，不能判消费者安全。

### E3：T13 一个实例变慢仍被持续分流

在独立部署中设置三个 frontend 或其他合适无状态服务实例。先证明访问确实覆盖多个实例，记录每个实例的实际流量份额，再挑其中一个施加方法/实例范围内的延迟。

Kubernetes Service 的连接复用、客户端长连接和 gRPC 多路复用会改变请求分布。不能把 1/N 当作无条件固定真值；应先固定负载连接策略，用基线每实例分流比例评价故障后的变化。必要时建立明确列出每个实例地址的实验代理配置，记录这是部署变体。

观测：被选实例请求明显变慢、健康检查仍通过、超过 T 后仍接收请求、总体高分位延迟没有恢复。保持一个健康业务对照，排除整个下游一起变慢。

修复：真正基于慢请求延迟的健康剔除，或能够实际响应延迟的负载策略。启用“仅按错误率”的异常剔除不保证解决慢而不报错的情况，不能看到 outlierDetection 字段就当成修复完成。

### E4：T12 探针访问依赖导致批量重启

先读取实际 Kubernetes 部署：至少两个副本、liveness 与 readiness 分开、探针调用路径明确。Docker Compose healthcheck 不能直接等同于 Kubernetes 自动重启逻辑。

若原版探针只看本进程，不把下游断连解释为缺陷。需要正例时，在实验变体中将 liveness 明确改为访问某个真实下游；固定 probe 周期、超时和连续失败阈值。

中断依赖足够覆盖探针触发预算。观测探针错误、Pod UID 与容器重启计数、服务实际不可用窗口。不要仅看 Pod 数量变化。

修复为 liveness 只看进程自身，readiness 依据业务策略单独检查。相同下游故障仍须证实，但不再要求 liveness 失败作为修复版的激活信号。

### E5：T03 超时预算与取消传播

候选链为 frontend → checkout → 某下游，最终链路取决于画像。先检查真实逐跳超时、重试与剩余预算传播，不因代码调用了 context.WithTimeout 就直接判断安全或不安全。

原版当前上下文传递是防护线索；尚未确认上游和 callee 的超时条件，不预设原版存在孤儿请求。

若允许实验变体：为指定调用配置明确的上游短预算、下游长预算，并在缺陷版的目标调用中确实断开取消传播；用标注的测试分支保存。修复版传播剩余预算并在后续处理前检查取消。

延迟要落在能形成“上游已放弃、下游仍执行”的实际时间窗。模板给出的预算中点只是候选参数；存在逐次超时、退避和取消时需要根据真实时序重新检查。

观测必须关联同一请求：上游返回超时的时间、下游是否收到取消、取消后是否继续执行及资源占用。不以跨机器两个未校时的日志时间戳单独证明严格先后。

## 12. 评价与交付

### 12.1 人工对照

评价单位是“模板版本 + 角色绑定 + 系统版本”，不是只有 15 个模板名称。人工先依据源码、部署和运行证据给出适用性及理由，再与自动结果比较。

记录 TP/FP/FN、查准率和查全率，同时报告 UNKNOWN 数量与占比。只在可人工判定样本上计算准确率，并同时公布总体覆盖率，防止把难样本全部返回未知来显得准确。未知样本不悄悄算成正确负例。

人工补充事实时，区分：自动事实匹配结果、加入人工事实后的匹配结果、最终动态结论。人工给出的角色/缺陷标签不得回灌同一测试作为自动能力证明。

### 12.2 对照表

每条深度模板尽量包含：正常基线；缺陷/原版的足够挑战；不足触发；防护/修复版的相同挑战。课程硬要求至少一组修改前后对照，不先承诺五条都实现完整修复。

表格保存版本、配置、负载、阈值、Exposure/Activation/Consequence、观测完整度、结论和证据链接。重复运行的每个结果都保留，不能只挑成功截图。

一个模板可以得到多个位置的不同结论，例如 accounting 已防护，而另一个消费者未知。禁止合并成“Kafka 模板不存在”。

### 12.3 分阶段实现

| 阶段 | 实现 | 完成标志 |
| --- | --- | --- |
| 1. 模板与事实 | 解析 15 条模板、版本校验、画像、证据和三值条件 | 能对所有模板给出解释与缺口，不能执行也如实说明 |
| 2. 匹配与编译 | 角色枚举、调用关系、首批适配器、调度器与观察器能力检查 | 对首条候选生成可审核的真实实验计划 |
| 3. 一条闭环 | T11 或预筛后更合适的一条，真实扰动、负载、取证与恢复 | 至少一个结论有完整证据，缺失时正确返回未知 |
| 4. 三态对照 | 同一链路的缺陷/未触发/修复或防护对照 | 结论能区分不同情况，恢复后重跑可复现 |
| 5. 五条与报告 | 扩展剩余候选、人工标注、重复实验、统计与失败记录 | 满足老师确认的五条口径，提交运行说明、测试与报告 |

先不按尚未明确的日期承诺周数。第一轮预筛是进入后续阶段的依据，若五条候选需要过多改造，应及时调整范围。

有意义的自动测试集中在三值逻辑、可选角色与数量约束、单位换算、未知证据、执行器不支持、静态动态矛盾和失败清理。少量实际集群实验验证适配与执行；不把模拟调度器测试当作真实缺陷验证。

## 13. 建议 API 与第一版目录

模板、画像、匹配、计划接口已在第一阶段提供，具体请求字段以 [服务说明](../platform/svc-defect-transfer/README.md) 为准；runs 与 comparisons 仍为后续计划接口：

- POST /api/defect-transfer/templates/import：导入版本化草稿和 OperationalSpec。
- POST /api/defect-transfer/profiles：采集或导入画像。
- POST /api/defect-transfer/matches：提交匹配任务。
- POST /api/defect-transfer/plans：编译实验，不直接执行。
- POST /api/defect-transfer/runs：执行已编译的计划，支持幂等键。
- GET /api/defect-transfer/runs/{id}：进度、证据、结论与清理状态。
- GET /api/defect-transfer/comparisons/{id}：修改前后或多次实验对照。

第一版包职责：domain（对象与规则）、profile（事实适配）、matching（角色与条件）、planning（参数与执行能力）、execution（阶段与恢复）、evidence（采集与覆盖）、verification（结论）、client（平台接口）、web（API）。不为了形式为每个简单数据类都增加接口。

## 14. 开工前只确认三个范围问题

1. 这 15 条 draft 模板能否作为 4.2 的输入，来源证据由谁后续补充？
2. “不少于五条验证”是否允许包含已防护、不适用或无法判定；若要求全部动态执行，是否允许明确标记的目标系统实验变体？
3. 能否使用独立实验命名空间修改部署、增加观测点和修复补丁，并通过故障调度服务执行？

默认方案是保留草稿、先做全量预筛、以证据驱动选择五条、只对明确支持的计划执行。以上范围未确认，不把原版系统一定有五类缺陷作为设计前提。
