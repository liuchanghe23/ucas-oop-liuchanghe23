## 一、选题说明

**一句话目标**：把"其他公司真实发生过的系统事故（缺陷）"，自动地"翻译"成一套能在我们自己被测系统上运行的故障实验，用来判断我们的系统是否存在同样的缺陷。

**本方向要做的事**：读入一份"缺陷模板"（来自事故复盘），结合被测系统的拓扑、配置和代码信息，找出系统里可能的风险点，生成符合 ChaosBlade 规范的故障实验，执行后判断"这个缺陷机制有没有被触发、预期后果有没有出现"。

**交付物**：一个可独立部署的服务 + 至少 1 个被测系统 + 不少于 5 条缺陷模板的验证 + 至少一组"修改前后对照"实验。

## 二、目标系统理解

本课题涉及两个"系统"，角色不同，先分清：

| 名称 | 角色 | 用什么写 | 我要对它做什么 |
|---|---|---|---|
| chaosblade-space-exploration | **平台**（我往里加功能） | Java / Spring Boot | 新增一个"缺陷迁移"服务，并调用它已有的数据与能力 |
| opentelemetry-demo | **被测系统**（我对它做实验） | 11 种语言（微服务） | 给它建"画像"，注入故障，验证结论 |

### 2.1 平台（chaosblade-space-exploration）的结构

平台由 6 个服务（+1 个统一启动器）组成，各自干一件事：

| 服务 | 端口 | 一句话职责 |
|---|---|---|
| svc-task-resource | 8101 | 管"数据"：系统、接口、拓扑、故障类型字典、任务（存 MySQL） |
| svc-task-executor | 8102 | 管"编排"：按流程调用别的服务 |
| svc-fault-scheduler | 8103 | 管"注入故障"：把故障实验交给 K8s 执行 |
| svc-result-processor | 8104 | 管"汇总结果"（目前还是空壳，只有 /hello） |
| svc-reqrsp-proxy | 8105 | 管"录制/拦截/回放"请求 |
| svc-topo | 8106 | 管"拓扑"：从链路追踪(Jaeger)里算出服务地图 |

平台里已有的几个关键"数据对象"（对应数据库表）：

- **System（被测系统）**：记录一个被测系统的名字、归属等。
- **Api（接口）**：记录某系统对外提供的某个接口（方法、路径、参数）。
- **ApiTopology / Node / Edge（拓扑）**：记录一张"调用地图"的节点和连线。
- **FaultType（故障类型字典）**：记录有哪些故障类型（CPU、内存、磁盘、网络、进程、内部），每种有哪些参数。

> 说明：平台已经能"算出拓扑"和"注入故障"，但**还不能把'缺陷模板'匹配到系统、也不能自动把匹配结果翻译成故障实验**——这正是 4.2 要补的核心。

### 2.2 被测系统（opentelemetry-demo）的结构

它是一个"天文商品网店"演示系统，约 30 个服务，用了 **11 种语言**（Go、Rust、C++、Java、Kotlin、C#、Node、Ruby、PHP、Python、Elixir），混用 gRPC、HTTP、数据库(Postgres)、缓存(Valkey)、消息队列(Kafka) 和特性开关(flagd)。这正是题目说的"异构系统"。

一条典型下单流程（简版）：

```
用户 → 前端(web) → 购物车/商品/推荐/广告 等
              → 结算 checkout
                  → 购物车 cart、货币 currency、支付 payment、物流 shipping、邮件 email
                  → 消息队列 kafka（可选）
```

**最重要的发现**：这个 demo 里自带 **20 个"缺陷开关"**（放在 flagd 配置文件里），每个开关对应一个真实的缺陷，例如：

- `cartFailure`：购物车按比例失败
- `productCatalogLockContention`：数据库锁竞争
- `recommendationCacheFailure`：缓存无界增长导致内存耗尽
- `adHighCpu`：CPU 被占满
- `emailMemoryLeak`：内存泄漏
- `kafkaQueueProblems` / `kafkaConsumerDead`：消息积压 / 消费者掉线

> 这给我们的验证带来极大便利：这些开关可以当作"已知缺陷的参考答案"，用来检验我们的自动匹配准不准；也可以用"开关打开/关闭"来构造"缺陷存在 / 未被触发 / 已被修复"的对照实验。

### 2.3 平台里"故障是怎么注入的"

故障实验最终交给 `svc-fault-scheduler`，格式是一段 ChaosBlade 配置，核心是：**对哪个目标(scope)、对什么(target)、做什么动作(action)、附加什么匹配条件(matchers)**。例如"对某个容器做网络延迟 100ms"。

现有执行流程（我们 4.2 要接进去的那条链）：

```
链路追踪(Jaeger) → svc-topo 算拓扑 → svc-task-resource 存进数据库
      ↓（4.2 补：缺陷模板匹配 → 生成故障实验）
svc-fault-scheduler 执行故障 → 观察指标变化 → 得出结论
```

## 三、需求分析（4.2 具体要做什么）

把题目要求拆成 5 个能力点：

1. **系统画像**：给被测系统建一份"档案"，包含拓扑 + 配置 + 代码信息。
2. **缺陷模板匹配**：把缺陷模板里的"因果角色"和"成立条件"，映射到系统里的具体对象（哪个服务、哪条调用）。
3. **故障场景生成**：按目标系统的实际情况，生成符合 ChaosBlade 规范的故障实验。
4. **执行与验证**：执行故障后，判断"缺陷机制是否被激活、预期后果是否出现、证据是否充分"。
5. **可扩展适配**：系统技术栈千差万别，要有一种"插拔式"适配机制，让新增一种技术栈不会破坏已有逻辑。

**验收指标**：1 个被测系统 + ≥5 条缺陷模板；自动匹配结果与人工判断对照（报告准确率、无法判定情况）；至少 1 组"修改前后对照"实验，能区分"缺陷存在 / 未被触发 / 已被修复"。

**要处理的"不确定结果"**：无法判断、执行器不支持、证据不足——这些不能用"是/否"糊弄，要能明确表达出来。

## 四、对象建模（初步）

围绕题目点名的 5 个核心概念，先各定一个对象：

| 对象 | 职责 | 关键内容（初步） |
|---|---|---|
| **SystemProfile（系统画像）** | 汇总被测系统的一切 | 系统信息 + 拓扑节点/连线 + 配置(端口/技术栈/资源) + 代码信息(框架/缺陷点) |
| **DefectTemplate（缺陷模板）** | 描述一条"事故套路" | 因果角色[]、成立条件[]、缺陷模式、证据来源 |
| **MatchResult（匹配结果）** | 记录"模板角色 → 系统对象"的对应 | 哪条角色对应哪个服务 + 置信度 + 状态(已匹配/未匹配/无法判定/执行器不支持) |
| **FaultScenario（故障场景）** | 一次可执行的故障实验 | 目标对象 + 故障类型 + 参数 + 生成好的 ChaosBlade 配置 |
| **VerificationConclusion（验证结论）** | 实验后的判断 | 是否激活、后果是否出现、证据是否充分 → 缺陷存在/未触发/已修复/证据不足 |

**对象之间的关系**（一句话版）：

```
SystemProfile  ──(被用来匹配)──►  MatchResult  ◄──(由它产生)──  DefectTemplate
      │                                 │
      │ 提供对象信息                      │ 匹配成功后
      ▼                                 ▼
（验证需要读指标）◄── VerificationConclusion ◄── 执行 ◄── FaultScenario（可执行的实验）
```

## 五、初步方案设计

### 5.1 总体流程

```
1. 建画像：把被测系统的拓扑 + 配置 + 代码信息整理成 SystemProfile
2. 匹配：对每条 DefectTemplate，用"适配器"把角色/条件映射到画像里的具体对象 → MatchResult
3. 生成场景：把匹配成功的对象，翻译成 ChaosBlade 实验配置 → FaultScenario
4. 执行：把 FaultScenario 交给 svc-fault-scheduler 执行
5. 验证：对比故障前后的指标/日志 → VerificationConclusion
6. 对照：自动匹配 vs 人工判断；开关开/关/改码 → 区分"存在/未触发/已修复"
```

### 5.2 可扩展适配机制（应对"异构"）

定义统一的"适配器"接口，每个技术栈（Java / .NET / Go / … / 数据库 / 消息队列）各写一个实现，通过注册表自动选择。这样**新增一种技术栈，只需新增一个类，不修改已有逻辑**（满足题目要求）。

### 5.3 阶段计划（对齐课程周次）

- **第 8-9 周（本报告）**：系统理解 + 需求分析 + 对象建模 + 初步方案。
- **第 13 周（第二版）**：实现匹配 + 场景生成 + 执行，跑通"存在/未触发"两种实验。
- **第 15-18 周（结题）**：补"已修复"对照、准确率统计、人工对照评价、报告终版。
