## 二、ChaosBlade Space Exploration（混沌工程平台）

### 2.1 定位

一个用于演示与实践混沌工程（Chaos Engineering）原理的 Spring Boot 微服务系统，围绕「故障空间探索」这一目标，提供故障注入、请求录制/拦截/回放、拓扑可视化、结果处理等能力。面向 Kubernetes 环境，通过 ChaosBlade CRD 与 Envoy Sidecar 完成真实故障与流量操作的编排。

### 2.2 技术栈

- Java 21、Spring Boot 3.5.5、Spring Cloud 2024.0.0
- Spring WebFlux（仅代理服务使用，响应式）
- Fabric8 Kubernetes Client 6.13.4（K8s API 交互，含 Pod exec WebSocket）
- MySQL 8（元数据/任务数据）、Redis 6.2（故障状态缓存）
- Jaeger（链路追踪，拓扑服务可选）
- Envoy Sidecar（请求录制/拦截/回放的数据面）
- 构建/规范：Maven、Spotless（googleJavaFormat）
- 部署：Helm Chart、Dockerfile、统一镜像（svc-unified）

### 2.3 总体架构

```
控制面 (Control Plane)
┌─────────────────────────────────────────────────────────────┐
│ svc-task-resource (8101)  任务资源/元数据管理 (MySQL)          │
│ svc-task-executor  (8102) 执行编排，调用代理完成录制/拦截/回放    │
│ svc-fault-scheduler (8103) ChaosBlade 故障注入编排 (K8s CRD+Redis)│
│ svc-result-processor (8104) 异步结果处理/汇聚                  │
│ svc-reqrsp-proxy   (8105) Envoy 录制/拦截/回放控制面 (WebFlux)  │
│ svc-topo           (8106) 拓扑可视化 + Jaeger 追踪             │
└─────────────────────────────────────────────────────────────┘
      │HTTP/JSON│      │JDBC│        │Redis│      │K8s API│
      ↓         ↓      ↓            ↓          ↓
   [MySQL]  [Redis]  [Kubernetes API Server]  [Jaeger]
                         ↓
                目标命名空间 (业务 Service + Envoy Sidecar)
```

服务间通过 HTTP/JSON 通信，主要链路：executor → proxy 下发指令；scheduler → K8s API 创建/删除 ChaosBlade CR；resource/result-processor 与各服务 REST 调用；所有服务提供 `/hello` 健康探活。

### 2.4 各模块职责与功能

#### （1）svc-task-resource（8101）— 任务资源管理
系统的事实中心，负责任务与元数据的持久化（MySQL）。实体模型覆盖：
- 系统/拓扑：`System`、`Api`、`ApiTopology`、`ApiTopologyNode`、`ApiTopologyEdge`
- 故障领域：`FaultType`、`FaultConfig`、`FaultConfiguration`、`FaultExecution`
- 检测/探针任务：`DetectionTask`、`ProbeTask`（对应 DTO）、`HttpReqDef`
- 执行与结论：`TaskExecution`、`TaskExecutionLog`、`TestResult`、`TestCase`、`TaskConclusion`、`TaskSlo`

主要控制器：`ApiController`、`SystemController`、`TopologyController`、`FaultTypeController`、`FaultConfigController`、`FaultConfigurationController`、`FaultExecutionController`、`DetectionTaskController`、`ProbeTaskController`、`HttpReqDefController`、`TaskSloController`。核心服务包括 `ApiTopologyService`（拓扑查询）、`ApiTopologyPersistenceService`（拓扑持久化）、`ExternalTopologySyncService`（外部拓扑同步）、`FaultExecutionService`（故障执行编排入口）等。

> 补充：`task/fault-detection-api-requirements.md` 定义了「故障空间检测」模块的后端接口需求（Base URL `/api`，统一返回 `{success, data, error}`，错误码含 VALIDATION_ERROR / NOT_FOUND / CONFLICT / DEPENDENCY_MISSING 等），是前端"新增检测"流程的服务端契约。

#### （2）svc-task-executor（8102）— 执行编排
任务执行的编排中枢。关键组件：
- `ExecutionOrchestrator`：执行编排器，串联故障配置、测试用例生成与测试执行
- `ProxyClient`：向 svc-reqrsp-proxy 下发录制/拦截/回放指令
- `KubernetesService`：K8s 交互（结合 `KubernetesProperties`）
- `LlmClient` + `SummaryService` + `TestCaseGenerationService`：基于 LLM 的测试用例生成与摘要
- `TopologyLayerService`、`FaultConfigQueryService`、`TestExecutionService`、`TaskExecutionLogService`
- 配置类：`ProxyProperties`、`RecordingProperties`、`SchedulerProperties`

控制器：`TaskExecuteController`、`TestExecutionController`、`TaskExecutionLogController`、`TopologyController`。

#### （3）svc-fault-scheduler（8103）— 故障注入编排
面向 ChaosBlade 的故障注入编排（Kubernetes CRD + Redis）。关键组件：
- `FaultsController`：提供 `/api/faults/execute`（传 spec 或完整 CR JSON）、`/api/faults/{name}/status`
- `FaultsService`：执行/查询故障的核心逻辑
- `SpecNormalizer`：将简化的 spec 规范化为 ChaosBlade 实验 CR
- `ChaosBladeApi`：封装 ChaosBlade CRD 的客户端
- `FaultRedisRepo`：故障状态缓存到 Redis
- `InfraConfig`：基础设施连接配置

#### （4）svc-result-processor（8104）— 结果处理
异步结果处理/汇聚服务。当前实现较精简（仅 `ResultProcessorApplication` + `HelloController`），是预留的异步汇聚扩展点。

#### （5）svc-reqrsp-proxy（8105）— 请求/响应代理（核心，WebFlux）
基于 Envoy 的「请求录制 / 智能拦截 / 回放」控制面，是系统最复杂的服务。通过 Fabric8 的 K8s Exec / ConfigMap / Deployment patch 对目标 Pod 的 Envoy Sidecar 进行配置。核心组件：
- **录制**：`RecordingService`、`RecordingStateService`、`RecordingConfig`/`RecordingSettings`、`K8sTapManager`、`TapCollector`、`TapConfigRenderer`、`TemplateBasedTapConfigRenderer`、`DirectTapReader`、`AutoCollectionTask`（定时采集）
- **拦截**：`InterceptionService`、`FixtureInterceptionService`、`PureInterceptionConfigRenderer`（纯拦截）、`FilterInterceptionConfigRenderer`（过滤式拦截）、`HybridService`/`HybridConfigRenderer`（混合模式）
- **回放**：`ReplayService`（配合 `ReplayRequest`/`ReplayResult`、`MockResponse`、`RecordedEntry`）
- **请求模式**：`RequestPatternService`、`RequestPatternAnalyzer`（识别服务请求模式，用于智能拦截）
- 辅助：`HttpRequestExecutor`、`AuthenticationService`、`TaskStateManager`、`EnvoyConfigDebugger`

控制器：`RecordingController`、`InterceptionController`、`FixtureController`、`HybridController`、`RequestPatternController`、`DirectTapController`、`TestController`。

#### （6）svc-topo（8106）— 拓扑可视化与追踪
拓扑可视化与链路追踪集成（Jaeger）。关键组件：
- 控制器：`ApiQueryController`、`TopologyCacheController`、`TopoVisualizationController`、`TraceUploadController`、`XFlowController`、`HomeController`
- 服务：`JaegerQueryService`（查 Jaeger）、`ApiQueryService`（API 查询/指标）、`TraceParserService`（解析 trace）、`TopologyConverterService`（Jaeger 数据→拓扑图）、`TopologyCacheService` + `TopologyAutoRefreshService`（拓扑缓存与自动刷新）、`XFlowConverterService`
- 模型：trace 域（`TraceData`/`SpanData`/`ProcessData`）、拓扑域（`TopologyGraph`）、实体域（`Node`/`Edge`/`Entity`/`RelationType`/`RedMetrics`）

#### （7）svc-unified — 统一镜像
通过环境变量 `SERVICE_NAME` 在一个镜像内按需启动任意一个服务，将 6 个镜像合并为 1 个，简化部署与运维（`UnifiedApplication` 内含服务映射）。

#### （8）common 公共模块
- `common-core`：`ApiResponse`（统一响应 `{code,message,data}`）、`DatabaseConfig`、`PageResponse`、`BusinessException`、`GlobalExceptionHandler`
- `common-test`：测试依赖与工具

### 2.5 基础设施与部署

- `infra/docker-compose.yml` + `infra/local/mysql-init/`：本地 MySQL/Redis 基础设施与初始化 SQL
- `helm/chaosblade-space-exploration/`：完整 Helm Chart（Deployment/Service/ConfigMap/Secret/RBAC/Ingress/ServiceAccount/namespace），支持内置或外部 MySQL/Redis
- `scripts/`：`start-all.sh`（打包并启动应用）、`build-images-from-jars.sh`、`build-unified.sh`、`start-unified.sh`、`deploy-helm.sh`、`uninstall-helm.sh`、`run-services.sh`、`spaceexploration.sql`
- RBAC：proxy 需 pods/get,list,watch、pods/exec、configmaps、deployments、services、events；scheduler 需 chaosblade.io CRD 及 events 权限

## 三、Mandol（智能体记忆系统）

### 3.1 定位

> Mandol: An Agglomerative Agent Memory System for Long-Term Conversations（面向长对话的聚合式智能体记忆系统）

一个原生的**进程内分层记忆系统**，为 LLM 智能体（尤其是长对话智能体）提供高效、可追溯的记忆构建与检索能力。在 LoCoMo 与 LongMemEval 两个长对话基准上达到 SOTA 精度（92.21% / 88.40%），并在服务端对比中相对最强基线获得 5.4× 检索加速、4.8× 插入加速。当前 `main` 分支是维护中的公开 Python 实现（v0.1.0），论文结果由冻结的 `paper-repro` 分支复现。

### 3.2 技术栈

- Python 3.12（`>=3.12,<3.13`）
- 数值/图：numpy、numba、scipy、networkx、rustworkx（核心图后端）、igraph、leidenalg（社区发现）
- 向量索引：faiss-cpu；持久化：rocksdict（RocksDB）
- 嵌入/模型：torch 2.8、transformers、sentence-transformers、huggingface_hub、flash-attn（cuda extra）
- LLM 客户端：openai、dashscope、tenacity、tiktoken
- NLP：spacy、nltk、jieba、rank-bm25、langchain
- 服务/数据：fastapi、uvicorn、pydantic、orjson、pandas、pyarrow
- 评估：bert-score、rouge、tabulate
- 工具链：uv、setuptools、ruff、pytest、Sphinx（文档）

### 3.3 核心设计思想（三大模块）

1. **分层记忆模型（Hierarchical Memory Model）**
   记忆组织为「基础记忆层 + 高层抽象记忆层」，两层统一表示为**结构化语义图**，所有记忆元素间具有可追溯关系。基础层用 memory unit、space、显式/隐式关系表示原始记忆；抽象层建模情景记忆（事件链）、语义记忆（实体图）与情感记忆（用户偏好）。

2. **进程内语义数据结构（In-Memory Semantic Data Structures）**
   `SemanticMap` + `SemanticGraph` 将键值、向量、图存储**原生融合**为一个统一混合检索接口，消除跨库 I/O 开销；支持 BM25/SPLADE/余弦多路检索与图遍历一体化。大数据量下通过 RocksDB 分层分页（tiered paging）把冷 `MemoryUnit` 载荷换出内存，同时保持检索索引与图状态常驻。

3. **智能量化检索（Smart Quantitative Retrieval）**
   用「查询自适应路由 → 两阶段去噪与冲突消解 → token 约束上下文生成」替代传统 RAG「召回-重排」范式；检索全程不调用 LLM。

### 3.5 核心公开 API

| 能力 | API |
|------|-----|
| 记忆单元 | `SemanticGraph.add_unit()` / `batch_add_units()` / `delete_unit()` |
| 显式关系 | `SemanticGraph.add_relationship()` / `delete_relationship()` |
| 稠密图检索 | `SemanticGraph.search_similarity_in_graph()` |
| 多路融合检索 | `MultiRetriever.smart_search()` |

> 顶层 `mandol/__init__.py` 将 `SemanticMap`/`SemanticGraph` 设为惰性导出，避免导入时立即加载 PyTorch/FAISS/SentenceTransformers。

### 3.6 持久化机制

默认载荷常驻内存，`save_graph()`/`load_graph()` 提供完整本地快照。RocksDB 是当前唯一支持的持久载荷后端：调用 `connect_to_l2()` 启用自动分层分页——稠密/BM25/SPLADE 索引、UID 映射、MemorySpace 归属、图拓扑常驻内存，冷载荷在超过高水位后异步驱逐，检索命中时再分页回缓存。

### 3.7 基准测试与工程结构

- `benchmark_locomo/`、`benchmark_longmemeval/`：论文复现基准（正式入口在 `paper-repro` 分支）
- `benchmark_self_host/`：当前自托管集成开发工作流，含 `locomo10` 与 `longmemeval` 的 `build_graph.py` → `retrieve.py` → `generate.py` → `evaluation.py` → `score.py` 流水线及 `scripts/run_*.sh`
- `examples/`、`tests/`、`docs/`（Sphinx，含 `current/` 与 `archive/` 双层文档）、`website/`
- `env.template`：OpenAI 兼容 provider 密钥、base URL、嵌入/重排端点配置模板

### 3.8 依赖与部署

- PyPI 安装：`pip install mandol`（v0.1.0）
- 源码环境：`uv sync`（开发/文档用 `--extra dev --extra docs --group spacy-model`；复现用 `--extra cuda`）
- CUDA/flash-attention 仅适配 Linux x86_64 / Py3.12 / Torch 2.8 / CUDA 12；不支持平台可省略

## 四、Ripple（集群发布-订阅系统）

### 4.1 定位

> A flexible pub-sub system for large-scale clusters（面向大规模集群的灵活发布-订阅系统）

一个去中心化、可配置拓扑的大规模发布-订阅（pub-sub）系统，由中国科学院软件研究所（ISCAS-SSG）开源（Mulan PSL v2）。服务器与客户端均支持**独立进程（standalone）**与**嵌入式（embedded）**两种部署模式，通过多种 Overlay 拓扑协议组织服务器集群，借助 CRDT 与混合逻辑时钟（HLC）解决并发冲突，并提供 Web 控制台管理配置与订阅。

### 4.2 技术栈

- Java（JDK ≥ 1.8）、Maven 多模块聚合
- 网络：Netty（自研 TCP 协议，请求/响应编解码器对）
- 存储：多后端可插拔（SQLite / 目录 / 持久内存 PM），带签名/副本容错策略
- 时钟：混合逻辑时钟（HLC）
- 冲突解决：CRDT（操作式 / 状态式 / Add-Win / Grow-Only）
- 内嵌 Web 控制台（Servlet）

### 4.3 总体架构（三模块）

```
Ripple (pom 聚合)
├── ripple-common   共享实体/哈希/存储/TCP 编解码/冲突解析
├── ripple-server   服务器节点（Overlay 拓扑 + CRDT + HLC + 分发器 + UI）
└── ripple-client   客户端（节点选择器 + TCP 处理器 + UI）
```

### 4.4 ripple-common（共享层）

- **实体 `entity`**：`AbstractMessage`、`UpdateMessage`、`DeleteMessage`、`IncrementalUpdateMessage`、`Ack`、`NodeMetadata`、`ClientMetadata`、`SystemInfo`、`Constants`（消息类型 update/delete/incremental_update，原子操作 add_entry/remove_entry）、`Item`
- **哈希 `hashing`**：`Hashing` 接口、`ModHashing`（取模）、`DefaultHashing`
- **冲突解析 `resolver`**：`MessageBasedResolver`、`LastWriteWinsResolver`（LWW）
- **存储 `storage`**（多后端可插拔，统一 `Storage` 抽象 + `StorageHelper`）：
  - `sqlite/`：`SqliteStorage` + Item/Message/Ack 服务 + `SqliteMaxNumberRecycleStrategy`
  - `dir/`：`DirBasedStorage` + 目录式服务 + 回收策略
  - `pm/`：`PMBasedStorage`（持久内存，含 `ItemEntry`、`PMCacheAdapter`）+ 对应服务
  - `ft/`（容错）：`ReplicaStrategy`、`SignatureStrategy`、`SignedReplicaStrategy`、`FileBased*` 实现、`SignatureHelper`
  - `RecycleStrategy`：最大条目数回收
- **TCP `tcp`**：`Encoder`/`Decoder`、`Message`/`MessageType`、`MessageEncoder`/`MessageDecoder`、`MessageHandler`、以及每种消息（Put/Get/Delete/Subscribe/Unsubscribe/IncrementalUpdate/Sync/Heartbeat/GetClientList/SystemInfo/Dispatch + 各 Response）对应的 `decoder/`、`encoder/`、`message/`、`handler/`

### 4.5 ripple-server（服务器节点）

- **入口**：`RippleServer`（工厂方法：`starProtocol` / `treeProtocol` / `expanderProtocol` / `gossipProtocol` / `hashingBasedProtocol`）、`Main`
- **核心 `core`**：
  - `Node`（节点主体）、`Worker`（工作线程）、`Tracker`（追踪器）、`HealthManager`（健康管理）
  - **Overlay 拓扑 `overlay`**（核心抽象 `Overlay`：`buildOverlay` / `calculateNodesToSync` / `calculateNodesToCollectAck`）：
    - `StarOverlay`（星型）
    - `TreeOverlay`（树型，含 `CompleteTree`、`TreeNode`）
    - `ExpanderOverlay`（扩展器，含 `BfsBuildStrategy`、`ThreeLayerBuildStrategy`、`SpanningTree`、`BuildStrategy`）
    - `GossipOverlay`（八卦/流言式，fanout）
    - `HashingBasedOverlay`（基于一致性哈希）
    - `TimeVaryingOverlay`（时变拓扑）
  - **分发器 `dispatcher`**：`ClientDispatcher` 接口 + `DefaultClientDispatcher`、`EqualDivisionClientDispatcher`（均分）
  - **CRDT `crdt`**：`Operation`、`OperationType`、`OperationBasedConflictResolver`、`StateBasedConflictResolver`、`AddWinConflictResolver`、`GrowOnlyConflictResolver`
  - **HLC `hlc`**：`HybridLogicalClock`、`HybridLogicalClockCoordinator`
- **TCP `tcp`**：`NettyServer`、`ServerChannelInitializer`、`ServerMessageHandler`，及服务端特有消息（AckRequest/AckResponse）与各请求处理器（Put/Get/Delete/Subscribe/Unsubscribe/IncrementalUpdate/Sync/GetClientList/SystemInfo/Heartbeat/Dispatch）
- **UI `ui`**：Servlet 控制台（`HomeServlet`、`AddConfigServlet`、`ModifyConfigServlet`、`RemoveConfigServlet`、`GetConfigServlet`、`GetSubscriptionServlet`、`IncrementalUpdateServlet`、`ClientClusterServlet`、`ServerClusterServlet`、`StyleServlet`、`PageGenerator`、`BaseServlet`、`Endpoint`）
- **helper**：`Api`（HTTP API）

### 4.6 ripple-client（客户端）

- **入口**：`RippleClient`（构造 + `start`/`stop`，`subscribe`/`unsubscribe`/`get`/`put`/`delete`/`incrementalUpdate`/`findOrConnectToServer`）、`Main`
- **节点选择 `core`**：`NodeSelector` 接口 + `HashingBasedSelector`（一致性哈希）、`LoadBalancedSelector`（负载均衡）、`Worker`
- **TCP `core/tcp`**：`ClientChannelInitializer`、`ClientMessageHandler`，及客户端响应处理器（`DispatchRequestHandler`、`SyncRequestHandler`、`Put/Get/Delete/Subscribe/Unsubscribe/IncrementalUpdate/SystemInfo/GetClientList ResponseHandler`）
- **UI `core/ui`**：控制台 Servlet（订阅管理 `AddSubscriptionServlet`/`RemoveSubscriptionServlet`/`GetSubscriptionServlet`、配置管理、`ServerInfoServlet`、`HomeServlet` 等）

### 4.7 关键机制

1. **多 Overlay 协议**：通过 `-Dprotocol=`（star/tree/expander/gossip/hashing）或工厂方法选择服务器集群拓扑，影响消息同步与 ACK 收集路径。
2. **冲突解决**：结合 CRDT（Add-Win / Grow-Only / 操作式 / 状态式）与 `LastWriteWinsResolver`，处理多副本并发更新（尤其 `incrementalUpdate` 的集合原子操作）。
3. **混合逻辑时钟（HLC）**：`HybridLogicalClock` + 协调器提供因果/全序时间，支撑去中心化节点间的一致性。
4. **多后端存储**：统一 `Storage` 抽象，SQLite / 目录 / 持久内存三后端，带最大条目回收与签名/副本容错。
5. **消息模型**：核心操作 `update` / `delete` / `incremental_update`，订阅模型为「应用名 + 键」（`app:key`）。
6. **双部署模式**：standalone（`java -jar -Did -Daddress -DapiPort -DuiPort -DstorageLocation -Dnodes -Dprotocol`）与 embedded（Java 代码实例化 `RippleServer`/`RippleClient`）。
7. **可观测/管理**：每节点/客户端提供 Web 控制台（`uiPort`）管理配置与订阅。

### 4.8 部署与基准

- 服务器集群示例：单机 3 节点（id=1/2/3，端口 3001-3003，UI 4001-4003）
- 客户端示例：`-DnodeSelector=loadbalance`
- 基准测试：README 提供 10 节点集群 + 100 客户端的压测方法（线程池建客户端、固定 QPS 写入、在 `DispatchRequestHandler`/`SyncRequestHandler` 提取时间戳计算延迟）

## 五、三项目对比总结

| 对比项 | ChaosBlade Space Exploration | Mandol | Ripple |
|--------|------------------------------|--------|--------|
| **架构风格** | 集中式微服务（控制面） | 单体 Python 库（进程内） | 去中心化集群（多拓扑） |
| **核心抽象** | 服务 + 控制器 + 实体/仓储 | MemoryUnit / SemanticGraph / Retriever | Node + Overlay + Storage + CRDT |
| **通信方式** | HTTP/JSON（REST） | 进程内函数调用（+ HTTP provider 调用 LLM） | 自研 TCP 协议（Netty） |
| **一致性** | 强一致（MySQL 事务） | 单进程（无跨节点一致性问题） | CRDT + HLC 最终一致 |
| **外部依赖** | MySQL、Redis、K8s、Jaeger、Envoy | PyTorch、FAISS、RocksDB、LLM API | 无（存储内嵌） |
| **扩展方式** | 水平扩缩容（K8s/Helm） | 单机内存/分层分页 | 集群节点 + 多 Overlay 拓扑 |
| **成熟度** | 演示/教学型微服务 | 研究发布（0.1.0 Alpha） | 研究原型（带压测工具） |

**一句话定位：**
- **ChaosBlade Space Exploration** 是「面向 Kubernetes 的混沌工程微服务演示平台」，价值在故障注入与流量录制/拦截/回放的可编排能力。
- **Mandol** 是「LLM 智能体长对话记忆的算法与工程实现」，价值在分层语义图 + 无 LLM 的量化检索带来的精度与速度。
- **Ripple** 是「可配置拓扑的去中心化发布-订阅系统」，价值在多种 Overlay 协议 + CRDT/HLC + 多存储后端的灵活组合。
